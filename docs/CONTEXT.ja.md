# 長いコンテキスト: モデルごとの上限と、設定する値

[English](CONTEXT.md)

`--max-context N`（設定ファイルの `args` に書きます）で、エンジンが持てる会話の長さの上限を決めます。このページでは、Abyss で動くモデルごとに、学習時の上限、256K までの実測、コンテキストが使うメモリ、PC に合わせて設定する値をまとめます。

## 1. モデルの上限

上限は、GGUF に書かれたモデル自身の `context_length` です。Abyss はこれより大きい値も止めませんが、その先はモデルが学習していない位置で動くことになり、答えは確かめていません。質が落ちる可能性が高いです。

| モデル | 上限（`--max-context` に入れられる値） | 上限までの伸ばし方 |
|---|---|---|
| DeepSeek V4 Flash 0731 | 1,048,576（1M） | 64K で学習、YaRN で 16 倍 |
| DeepSeek V4.1 Flash 1017 | 1,048,576（1M） | 64K で学習、YaRN で 16 倍 |
| GLM-5.3-Flash | 1,048,576（1M） | （GGUF の記載どおり） |
| Qwen3.8-Flash-Next | 262,144 | そのまま |
| Qwen3.8-27B | 262,144 | そのまま |
| Ornith-1.5-122B / 35B / 397B | 262,144 | そのまま |
| Laguna-S-2.1 | 262,144 | 8K で学習、YaRN で 32 倍 |
| Qwen3.5-9B QSA、Ornith-1.5-9B QSA、MiMo-V2.6-Distill-Qwen-9B | 262,144 | そのまま |
| SenseNova-Loop-9B | 524,288（512K） | 256K がそのまま、YaRN で 2 倍 |

測定に使った pack の元の GGUF から読みました（`<arch>.context_length`）。256K（262,144）は、上のどのモデルでも上限の内側です。それより先まで行けるのは、V4・V4.1・GLM-5.3-Flash（1M まで）と SenseNova-Loop-9B（512K まで）です。

## 2. 実測（RTX 5090 32 GB、RAM 123 GB）

各測定は、サーバー（`/v1/chat/completions`、temperature 0、モデルのチャットテンプレート）に 1 回送ったものです。

- **プロンプト:** 実際のソースコード約 60K / 125K / 250K トークン。
- **仕掛け:** プロンプトの 2%・50%・97% の位置に秘密の文字列を 3 つ、それに小さな関数を 1 つ埋め込み、その関数の値を答えさせます。
- **「OK」の基準:** 秘密 3 つと関数の値が全部合っていること。
- **速さ:** 「プロンプト」はサーバーが返すプロンプトの tok/s、「生成」はコンテキストが埋まった状態での生成の tok/s です。
- iGPU なしで、それぞれ greedy で 1 回だけ測りました。

| モデル（ファイル） | 64K | 128K | 256K |
|---|---|---|---|
| V4 0731 UD-Q2_K_XL | OK / 2,815 / 66.8 | OK / 2,686 / 70.7 | OK / 2,336 / 65.6 |
| V4.1 Compact JA256 | OK / 2,356 / 57.0 | 秘密 OK・関数× / 2,678 / 68.9 | 秘密 OK・関数× / 4,651 / 67.5 |
| GLM-5.3-Flash Maya-S-v2 IQ2_XXS | OK / 2,247 / 36.0 | OK / 2,299 / 39.9 | OK / 2,127 / 30.0 |
| Qwen3.8-Flash-Next UD3.1 IQ3_XXS | OK / 2,830 / 111.2 | OK / 2,898 / 124.6 | OK / 2,562 / 84.2 |
| Ornith-1.5-122B 24G64G | OK / 2,186 / 53.0 | OK / 1,510 / 60.6 | OK / 1,608 / 41.5 |
| Ornith-1.5-35B-A3B Q4_K_M | OK / 1,888 / 299.8 | OK / 926 / 254.8 | OK / 3,857 / 170.6 |
| Qwen3.8-27B UD-Q4_K_XL、KV fp16 | OK / 1,892 / 73.6 | OK / 1,274 / 51.7 | OK / 1,530 / 25.2 |
| Qwen3.8-27B UD-Q4_K_XL、`--kv int8` | - | - | OK / 1,410 / 38.4 |
| Laguna-S-2.1 UD-IQ4_XS、KV fp16 | OK / 526 / 45.5 | 秘密 OK・関数× / 258 / 37.2 | OK か秘密 2/3（実行ごとに変わる）/ 2,347 / 19.8 |
| Laguna-S-2.1 UD-IQ4_XS、`--kv int8` | - | - | OK / 2,329 / 20.9 |

**表の見方**
- 各マスは「結果 / プロンプト tok/s / 生成 tok/s」です。
- バージョン:
  - 64K と 128K は v1.3.150（2026-11-15）です。
  - 256K は v1.3.174 です。ただし `--kv int8` の行と、27B / Laguna の fp16 の 256K は v1.3.175（2026-11-19）です。
- バージョンが違うプロンプト速度は比べられません（あいだにプロンプト処理の改善が入っています。Laguna の 128K → 256K の伸びはそのためです）。
- V4.1 Compact JA256 の関数の答えは、128K でも 256K でも同じ間違い（196）です。長さのせいではなく、この量子化の読み取りの弱さです。

**わかったこと**
- 256K では全モデルが起動して最後まで答え、エラーはありませんでした。
- 生成は、コンテキストが埋まるほど遅くなります（1 トークンごとにキャッシュ全体を読むため）。
- いちばん落ちるのは、キャッシュが重みを VRAM から押し出すモデル（Qwen3.8-27B、Laguna）です。§3 を見てください。

## 3. コンテキストが使うメモリ

KV キャッシュ（モデルが会話を覚えておく分）は、起動時に `--max-context` 全体の分を VRAM に確保します。その残りがモデルの重み（エキスパートの置き場）に回ります。v1.3.176 からは、CUDA の GPU 1 枚で動かす qwen35 系（Qwen3.8・Ornith・Laguna）は、KV を会話が伸びた分だけ割り当て、まだ使わない分を KV が必要になるまで重みに貸します（`--kv-elastic`、既定で有効。`--kv-elastic 0` で下の固定の配置）。下の表は固定の配置、つまりコンテキストが全部埋まったときの数字です。数字はエンジンの起動ログから取りました。

| モデル | 128K の KV | 256K の KV | エキスパートより前に使う VRAM（256K） |
|---|---|---|---|
| DeepSeek V4 0731 | 0.86 GB | 1.70 GB | 8.91 GB |
| DeepSeek V4.1 1017 | 0.40 GB | 0.79 GB | 8.85 GB |
| GLM-5.3-Flash | 1.78 GB | 3.32 GB | 11.03 GB |
| Qwen3.8-Flash-Next | 3.00 GB | 6.00 GB | 11.35 GB |
| Ornith-1.5-122B | 3.25 GB（`--kv q4_0` で 0.91） | 6.50 GB | 13.21 GB |
| Ornith-1.5-35B | 2.75 GB | 5.50 GB | 8.14 GB |
| Qwen3.8-27B（dense） | 8.50 GB | 17.00 GB（`--kv int8` で 9.03） | FFN（9.93 GB）より前に 25.93 GB |
| Laguna-S-2.1 | 6.35 GB | 12.35 GB（`--kv int8` で 6.56） | 17.07 GB |

**表の見方**
- KV は `--max-context` にほぼ比例します。コンテキストを半分にすれば、KV もほぼ半分です。
- 「エキスパートより前に使う VRAM」は、RTX 5090 での「dense の重み＋KV＋作業用バッファ」です。作業用バッファは小さいカードでは小さくなるので、上限の目安として見てください。
- カードの残りがエキスパートの置き場です。入りきらないエキスパートは RAM から読みます（遅くなりますが、答えは変わりません）。

**モデルごとの意味**
- **DeepSeek V4 / V4.1、GLM-5.3-Flash:** キャッシュが小さいモデルです（MLA や圧縮した注意）。256K にしても、短いコンテキストより 1〜3 GB 増えるだけで、長さはメモリにほとんど響きません。
- **Qwen3.8-Flash-Next、Ornith:** 128K あたり 3 GB ほどです。256K にすると、128K よりエキスパートの置き場が 3 GB ほど減ります。
- **Qwen3.8-27B、Laguna:** キャッシュが大きいモデルです。32 GB のカードで 256K にすると、fp16 の KV が重みを押し出します。
  - 27B: FFN のうち 5.2 GB が RAM に移り、生成が 51.7 → 25.2 tok/s に落ちます。
  - Laguna: エキスパートの枠が 1 層あたり 97 → 66 に減ります。
  - このとき起動ログに、`--kv int8` で何 GB 空くかを書いた `hint:` が 1 行出ます。
  - 27B に `--kv int8` を付けると FFN が全部 VRAM に戻り、生成は 38.4 tok/s になります。

`--kv int8` / `q4_0` は、キャッシュを少ないビット数で持ちます。精度がわずかに落ちます（KL の数字は[マニュアルの `--kv` の行](MANUAL.ja.md)にあります）。既定は fp16 のままです。

## 4. 設定する値

| カード | 動くことを確かめた設定 |
|---|---|
| 32 GB（RTX 5090 クラス） | §2 の全モデルで `--max-context 262144`。Qwen3.8-27B は `--kv int8` を足す（生成 25 → 38 tok/s） |
| 32 GB で、V4 / V4.1 / GLM を 256K より長く | モデルとしては 1M まで可能。ここでは測っていない（下のユーザー報告を参照） |
| 16 GB | `--max-context 131072` を V4.1 Compact JA256、Qwen3.8-Flash-Next、Ornith-1.5-122B（`--kv q4_0`）で確認。どれも正答で、生成は 39.8 / 77.9 / 38.8 tok/s。256K は未測定 |

**注意**
- 16 GB の行は、RTX 5090 を `STRATA_GLM_VRAM_GB=16` で 16 GB に制限して測ったものです（RAM は 123 GB のまま）。本物の 16 GB のカードではありません。
- ほかのカードでは、§3 から見積もってください。
  - カードに要るのは、「エキスパートより前に使う VRAM」に、エキスパートを置く余裕を足した分です。コンテキストを短くするなら、その分を KV の列から差し引きます。
  - 本当の数字は起動ログに出ます。
  - 入りきらないと、エンジンは `not enough VRAM for the expert pool` で止まります。そのときは `--max-context` を下げるか、`--kv int8` / `q4_0` を足してください。

**ユーザー報告**
- DeepSeek V4 Flash を Radeon AI PRO R9700 で 393K（291K のプロンプトを 279 tok/s で読み、生成 19.5、issue #1）。
- ほかの報告は [MODELS.ja.md §3](MODELS.ja.md#3-ユーザー報告参考) にあります。

## 5. 関連する動き

- 答えに使える残りが min(1024, コンテキストの 1/4) トークンを下回るプロンプトは、HTTP 400「prompt is too long」で断ります（v1.3.172 から。`STRATA_FIT_FLOOR` で変えられます）。Claude Code のようなコーディングエージェントは、これを受けて会話を圧縮します。
